Project Overview

Debugged and verified an 8-point moving average processor using an industry-style SystemVerilog verification environment. The testbench architecture mirrors the UVM (Universal Verification Methodology) pattern used in professional ASIC and FPGA design flows, with a structured driver, monitor, scoreboard, and mailbox-based inter-process communication.

The project involved two phases: Phase 1 — debugging the provided moving average design using the testbench to identify and fix timing bugs; Phase 2 — integrating a real BRAM model and adding a new testcase that verifies the design end-to-end using data loaded from a memory initialization file.

Moving Average Algorithm

The 8-point moving average computes a sliding window sum over the input sequence, producing one output per clock cycle once the window is filled:

A[n] = ( x[n] + x[n-1] + x[n-2] + x[n-3] + x[n-4] + x[n-5] + x[n-6] + x[n-7] ) / 8

The design reads 16-bit unsigned integer samples from a 1024-deep BRAM with 1-cycle synchronous read latency. The o_valid signal is only asserted after the first 8 samples are consumed. The running sum uses a sliding window buffer — on each new sample, the oldest value is subtracted and the newest is added, keeping computation O(1) per cycle.

Verification Architecture

The testbench follows a structured UVM-inspired hierarchy with four main components communicating through SystemVerilog mailboxes and a virtual interface. This separates concerns cleanly — stimulus generation, output observation, and result checking are fully decoupled.

Component 01

Base Test

Top-level orchestrator. Builds and connects all environment components, selects testcase via test_num, manages reset/start sequences, and reports PASS/FAIL.

Component 02

Driver

Generates input stimulus. In testcase 0, forces BRAM data into the DUT. In testcase 1, sends only the golden dataset to the scoreboard — the actual BRAM drives the DUT.

Component 03

Monitor

Observes DUT outputs — samples o_valid and o_data on each cycle where valid is asserted, and forwards samples to the scoreboard via mailbox.

Component 04

Scoreboard

Compares DUT output against golden reference values computed from the input sequence. Tracks pass/fail count and prints CORRECT or MISMATCH for each output with BRAM address context.

Component 05

BRAM (mem.sv)

1024-deep × 16-bit synchronous Block RAM with 1-cycle read latency. Initialized from init.mem using $readmemh. Write-enable held low during verification.

Component 06

DUT Interface

Virtual interface (dut_if) connecting testbench components to DUT signals. Clocking blocks synchronize stimulus to clock edges. Force/release used to bypass clock/debounce modules in simulation.

Bug Identification & Debug

The provided moving average design contained a timing bug between the always_ff sequential block and the always_comb combinational block. Careful waveform inspection and scoreboard mismatch messages were used to isolate the issue.

Bug Identified

BRAM Read Latency Not Accounted For

The moving average core was consuming BRAM data before it was valid due to the 1-cycle synchronous read latency. The recv_count was advancing in the same cycle that the address was issued, causing the datapath to process stale data — producing incorrect running sums and invalid o_data outputs that the scoreboard flagged as mismatches.

Fix Applied

The data consumption logic was gated on recv_count < req_count — ensuring that the FSM only processes a sample when the BRAM has had a full cycle to return valid data after the address was issued. This correctly decouples the read request count from the receive count by exactly one cycle, matching the BRAM's synchronous latency specification.

Phase 2 — BRAM Testcase Integration

After verifying the fixed design with testbench-forced data, a second testcase (test_num = 1) was implemented that uses the actual BRAM model instead of forced stimulus.

The steps taken to add the new testcase in base_test.sv were: reset the DUT, call vif.disable_bram_data_force() to release the testbench force on i_bram_data, assert the start signal, then run the driver, monitor, and scoreboard concurrently using a fork...join_any construct. The driver in this mode sends only the golden dataset to the scoreboard — it does not drive the BRAM lines, which are now controlled entirely by the DUT.

The mem.sv BRAM module was completed with $readmemh("init.mem", mem) to preload the 1024-sample dataset. The analog waveform view of i_bram_data and o_data confirmed correct moving average behavior — the rough, varying BRAM input produces a smooth, averaged output waveform.

Both testcases passed with 0 scoreboard mismatches across all 1,017 moving average outputs verified from a 1,024-sample BRAM dataset.

The verification environment automatically detected and reported the timing bug, and confirmed correct operation after the fix — demonstrating the value of structured, self-checking testbenches over manual waveform inspection.

Key Takeaways

Structured verification scales: Adding testcase 1 required minimal effort because the driver, monitor, and scoreboard were already built. Switching from forced stimulus to real BRAM required only disabling the force and updating the test selector — the checker logic was completely reused.

BRAM latency is a real constraint: The 1-cycle synchronous read latency must be explicitly handled in the FSM. Ignoring it causes silent data corruption that is only visible through careful waveform analysis or a self-checking scoreboard.

Mailbox-based IPC: The driver-to-scoreboard and monitor-to-scoreboard mailboxes allow the golden reference and DUT output to be compared asynchronously — neither component needs to know about the other's timing, making the testbench robust to timing variations.
